# Deployment

EnergyOS is a Next.js Node server and a PostgreSQL database. No containers are needed anywhere.

| Where | Database (`DATABASE_URL`) | Background jobs |
|---|---|---|
| Your laptop (`pnpm dev`) | `pglite:./data/pglite` — PGlite, the Postgres engine embedded in Node; nothing to install | in-process |
| Tests | a fresh PGlite per test file, or a real server with `TEST_DATABASE_URL` | — |
| Render (the reference deployment) | Render PostgreSQL, linked by the Blueprint | in-process, plus optional external tick |
| Any Linux VM | PostgreSQL on the VM or managed (Supabase, Neon, RDS …) | in-process (systemd keeps it running) |
| Serverless (Vercel …) | managed PostgreSQL | external scheduler calling `/api/cron/tick` |

## 1. Local development

Requirements: Node.js 20.9+ (tested on 22), pnpm 10.

```bash
pnpm install
cp .env.example .env
pnpm db:setup        # creates ./data/pglite, applies migrations, seeds the demo
pnpm dev             # http://localhost:3000
```

`pnpm db:reset` deletes the local PGlite directory and starts again. To develop against a real server instead, set `DATABASE_URL=postgres://…` in `.env`.

## 2. Render (reference deployment)

`render.yaml` in the repository describes the whole deployment: a free Node web service in Singapore and a free PostgreSQL 17 database on Render's private network. Secrets are generated by Render (`DEMO_PASSWORD`, `CRON_SECRET`) or linked from the database (`DATABASE_URL`); none are stored in the repository.

**First deployment**

1. Push the branch the Blueprint names (`release`).
2. Render Dashboard → **New → Blueprint** → pick this repository and the `release` branch → review → **Apply**. Render creates (or adopts, if it already exists) the database, builds the service and starts it.
3. The start command runs `scripts/db-setup.ts` before `next start`: migrations are idempotent, and the demo is seeded only into an empty database.
4. Open `https://<service>.onrender.com/api/health` — it answers `{"status":"ok","db":"ok"}` once the database is reachable.

**Every later deployment**: push to `release`. Render builds and deploys it; migrations run on start.

**What the free plan means**

- The web service sleeps after about 15 minutes without traffic and takes roughly 30–50 seconds to wake. While it sleeps, in-process jobs (IEX prices, meter-offline alerts, audit sealing) pause; they catch up on the first request after waking. To keep them running, point any scheduler at the tick endpoint every 10 minutes:
  ```bash
  curl -X POST -H "Authorization: Bearer $CRON_SECRET" https://<service>.onrender.com/api/cron/tick
  ```
  (`CRON_SECRET` is on the service's Environment page in Render.) cron-job.org or a scheduled GitHub Action works.
- The free database expires 30 days after creation unless upgraded (Render emails before it does). Upgrade it in the dashboard (Basic 256 MB, about US$6/month) to keep it, or export first with `pg_dump` (below).
- For a pilot: Starter web service (about US$7/month, always on) and a paid database. Change `plan:` in `render.yaml` and push.

## 3. Any Linux server (no containers)

```bash
# once
sudo apt-get install -y postgresql
sudo -u postgres createuser --pwprompt energyos
sudo -u postgres createdb -O energyos energyos

# app
git clone <repo> energyos && cd energyos
pnpm install --frozen-lockfile
cp .env.example .env   # set DATABASE_URL=postgres://energyos:…@localhost:5432/energyos
                       # COOKIE_SECURE=true, SEED_DEMO_USERS=false (or a private DEMO_PASSWORD)
pnpm db:setup
pnpm build
```

Run it under systemd so it restarts on failure (`/etc/systemd/system/energyos.service`):

```ini
[Unit]
Description=FactoryTwin EnergyOS
After=network.target postgresql.service

[Service]
WorkingDirectory=/srv/energyos
EnvironmentFile=/srv/energyos/.env
ExecStartPre=/srv/energyos/node_modules/.bin/tsx scripts/db-setup.ts
ExecStart=/srv/energyos/node_modules/.bin/next start -p 3000
Restart=always
User=energyos

[Install]
WantedBy=multi-user.target
```

Put a TLS reverse proxy in front, for example Caddy (`/etc/caddy/Caddyfile`): `energy.example.in { reverse_proxy localhost:3000 }`.

## 4. Serverless hosts

The app runs on serverless platforms with two settings: `DATABASE_URL` pointing at a managed PostgreSQL (use the provider's pooler; set `DB_PREPARE=false` for transaction-mode pools such as Supabase port 6543), and `ENERGYOS_JOBS=false` with an external scheduler calling `/api/cron/tick`. The server warns at start-up if it detects a serverless runtime with an embedded database.

## 5. Environment reference

| Variable | Default | Purpose |
|---|---|---|
| `DATABASE_URL` | `pglite:./data/pglite` | `postgres://…` (production) or `pglite:<dir>` (local) |
| `DB_POOL_MAX` | `10` | Connections per server instance. Keep instances × pool under the database's connection limit (free Render: about 97). |
| `DB_PREPARE` | `true` | `false` for transaction-mode connection poolers |
| `COOKIE_SECURE` | `false` | `true` behind HTTPS (also enables HSTS). The server refuses to start with `true`, demo users and the published default password. |
| `SEED_DEMO_USERS` / `DEMO_PASSWORD` | `true` / `energyos-demo` | Demo logins. `false` for any real plant. |
| `ENERGYOS_JOBS` | `true` | `false` turns off in-process jobs (use the tick endpoint instead) |
| `CRON_SECRET` | – | Enables `POST /api/cron/tick` (Bearer) |
| `INDIA_MARKET_FEED` | `iex` | `off` for a plant network without internet. Behind an outbound proxy, start Node with `NODE_USE_ENV_PROXY=1`. |
| `ANALYSIS_DEBOUNCE_MS` | `60000` | Delay before re-analysing after meter data arrives |
| `ALLOW_PRIVATE_WEBHOOKS` | `false` | Allow alert webhooks to private hosts (an internal SMS/WhatsApp gateway) |
| `SMTP_URL` | – | Turns on email alerts. `smtps://user:pass@host:465` (TLS) or `smtp://user:pass@host:587` (STARTTLS is required). URL-encode special characters in the password. |
| `ALERT_EMAIL_FROM` | `EnergyOS <alerts@localhost>` | Sender. Must be an address your mail provider lets you send from. |
| `APP_URL` | – | Public address of the app, used for links in emails |
| `SMTP_ALLOW_INSECURE` | `false` | Plain SMTP without TLS, for a relay on the same machine only |

## 6. Running more than one instance

Safe by design:

- Writers that check before they write (overlapping heats, version numbers, approvals, analysis runs, scenario resets) take a per-factory PostgreSQL advisory lock inside their transaction.
- The audit hash chain is sealed by one sealer at a time (advisory lock) and ordered by its own sequence, so out-of-order commits never break verification.
- Login throttling and API rate limits are counters in PostgreSQL, shared by every instance.
- "Re-analyse this factory" is a flag in the database that exactly one instance claims; nothing is lost on restart.

Still per instance: the ingest flood guard (an in-memory first line of defence before any database work) and the 15-second start-up tick. Sessions are database rows, so no sticky sessions are needed.

## 7. Operations

- **Health**: `GET /api/health` (database round-trip). Render uses it as the health check.
- **Logs**: Render Dashboard → service → Logs; on a VM, `journalctl -u energyos -f`.
- **Backups**: `pg_dump "$DATABASE_URL" -Fc -f energyos-$(date +%F).dump`; restore with `pg_restore -d "$DATABASE_URL" --clean energyos-….dump`. Paid Render databases also take daily snapshots.
- **Schema changes**: edit `src/db/schema.ts`, run `pnpm db:generate`, commit the migration. It is applied on the next start.
- **Meter connection**: Factory settings → issue an ingest token → run the meter gateway (`gateway/README.md`) on a PC or Raspberry Pi on the plant network. It reads a Modbus TCP meter, buffers offline and pushes to `POST /api/ingest`.
- **Email alerts**: set `SMTP_URL`, `ALERT_EMAIL_FROM` and `APP_URL` (any SMTP provider: Amazon SES, Brevo, Mailgun, Zoho, Google Workspace). Then the owner enters up to five addresses under Factory settings → Alerts and presses "Send test alert". Some hosts block the usual SMTP ports on free plans; most providers also listen on port 2525 (`smtp://…:2525`).
- **Integrations**: Factory settings → Integration API → create a read-only key; endpoints are described at `/api/v1/openapi.json`.

## 8. Capacity

Measured earlier on SQLite at about 124 days of one-minute data (178,560 readings): 30-day trend 16 ms, one-day summary 27 ms, seven-day summary 131 ms. PostgreSQL with the same indexes is in the same range for these queries. A daily rollup table is not needed until a seven-day summary passes about half a second or several sites share one database.
